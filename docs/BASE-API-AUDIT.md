# Base-client API and readiness audit

**B7d status: OPEN — preliminary repository audit, October 23, 2026.** This records the implemented surface and known evidence; it does not declare beta stability or authorize extensions/publication. B7b still needs an existing application and executed [trial](APPLICATION-TRIAL.md). B7c must supply scale, browser-memory and lower-powered-environment evidence before the final decision.

The reviewed B7a baseline passed 403 tests, 25 browser scenarios and isolated JavaScript/TypeScript/Angular consumers; see its [review record](reviews/2026-10-22-typed-snapshots.md). Those results cover the repository fixtures, not an arbitrary real application. The recorded published release is alpha.5; provider registration/assignment, polling and inferred snapshots are implemented on main and queued for a batched release. Use commit/hash-identified tarballs when evaluating those additions.

## Supported surface and defaults

The GraphQL package's HTTP default requires an absolute HTTP(S) endpoint and a platform with its Web APIs. Core imports no platform, framework, GraphQL or HTTP API; consumers enabling its timers supply the relevant scheduler capabilities. Packages ship ESM JavaScript with optional TypeScript declarations. Angular's supported peer major is 21 (`^21.2.25`), GraphQL's is 16 (`^16.14.2`), and matching Tandrove alpha versions are required. The tested baseline includes TypeScript 5.9.3/RxJS 7.8.2; Node tooling requires >=22.14.0, with Node 24 in release CI. No CommonJS, older-Angular or SSR-hydration compatibility is established by these checks.

## Public exports with provisional contracts

Exported does not yet mean stabilized. `StateStore`, `AcquisitionClient`, decoded changes, canonical selection/address utilities, `AcquisitionSource` and `ingest` are available to adapter authors but remain provisional. The fake whole-resource and in-process event adapters prove boundary behavior. They do not provide a production REST/stream protocol, routing, reconnect or persistence product.

Ingestion requires validated nonempty patches for known records with active ownership and established membership; it cannot change list membership. All writes still pass coverage, scope, generation and atomic-commit validation. A custom bound acquisition provider serves its declared resource address, not arbitrary resources. GraphQL transport providers can serve multiple resources. New transports must preserve ownership and decoding boundaries; they cannot bypass the store through direct mutation.

Provider scope has no implicit dependency graph, service aliases or process-global cache. Factories compose dependencies explicitly during bootstrap, and failed initialization is memoized. These omissions are documented boundaries, not empty advertised implementations. B7d must decide which low-level APIs stay explicitly experimental for beta; the current audit does not freeze them.

## Unsupported and separately planned

- Schema inspection rejects custom scalars, abstract types/interfaces/unions, OneOf inputs and custom directives anywhere in the supplied SDL. The planner expects `Query` and does not traverse list items in a resource path. Generated typing does not expand that supported runtime subset.
- Runtime acquisition supports singleton objects, keyed top-level object lists, nested objects and scalar lists. Nested object-list decoding, unkeyed/null object-list entries, pagination merging and arbitrary joins are unsupported. Identity fields must be configured non-null scalars/enums without arguments.
- Mutation planning, a public form-draft manager, automatic write retries, optimistic mutation reconciliation, durable commands and offline recovery are absent. Demo forms demonstrate an application-owned policy with explicit Save.
- Production WebSockets/SSE, server authoritative revisions, vector clocks, reconnect replay, Redis/Socket.IO adapters, server companion, React/full RxJS adapters and SSR hydration are future work. Local request generations cannot establish end-to-end consistency across writers or server instances.
- Retention is elapsed inactive lifetime, not a byte/count limit or active-cache memory budget. Polling has no browser visibility policy. No production-scale performance or memory budget is accepted yet.

These features are not automatically added to the base milestone. An existing application's dependency on one is a real integration finding that must be considered before claiming readiness.

## Migration and integration traps to verify

1. **Published versus checkout bytes:** B4–B7a are absent from registry alpha.5 even while local manifests still say alpha.5. Install matching trial tarballs and record hashes; do not infer availability from a version string alone.
2. **Partial values stay partial:** remove old explicit `watch<Result>(...)` arguments and infer from a typed bound definition. Use `SnapshotData<ResultOf<...>>` for consumer data. Neither `ready` nor `complete` narrows to full schema data. The new output-based type aliases no longer support declaration merging; use application-owned intersections if needed.
3. **Session ownership is explicit:** credentials in dynamic headers are not state identity. Dispose/recreate clients on authorization changes. Changing credentials inside an existing transport function cannot be detected by shared-authority checks. Resource scopes are application-supplied isolation metadata, not server authorization.
4. **Lifetime differences matter:** unsubscribe does not release a query handle; a retained disposed handle still exposes its last snapshot. Signal bridges do not dispose readers. Angular owned-query replacement releases its old handle, but its poll registrations do not transfer to the new binding. Clients dispose before provider scopes.
5. **Policies cannot split one shared resource:** groups/tokens are configuration, not state keys. Same-address consumers must agree on authority, deadline, freshness and retention; polling defaults may differ. Duplicate names across `resourceGroups` and legacy `requestPolicyGroups` reject. Disabled transport is an error, not offline/cache-only mode.
6. **Refresh semantics remain distinct:** membership mismatch needs `refreshList()`; opted-in membership-age expiry separately enables full-selection reacquisition. `invalidate()` without a target covers the caller's selection, not every cached extension. Narrow reads may fail after successful sibling writes commit.
7. **Errors have different ownership:** handle `error` follows its latest invoked attempt and may remain after another consumer repairs shared fields. Inspect field/resource errors and freshness too. Diagnostics callbacks are isolated from acquisition; there is no unified tracing/devtools API yet. Preserve actionable distinctions instead of flattening every state into “loading” or “failed.”

## Audit findings and final decision gates

This slice corrects stale guide claims that runtime data was only untyped JSON and polling was unimplemented, relative-URL examples incompatible with the HTTP constructor, and install introductions describing published alpha.5 as an unpublished candidate. Rechecking the acquisition/planner guides, package READMEs, freshness/retention examples and release record confirms those corrections match the source and recorded publication evidence. They were documentation defects; this audit has not established a new runtime correctness defect or ruled out defects through a production trial.

The initial [scale/lifecycle baseline](PERFORMANCE.md) now records PERF-01: large-list refresh latency requires a separately reviewed profiling/fix task and a rerun. The bounded browser heap results and CPU-throttled profile are useful evidence, but do not supply a real application or physical lower-powered-device result.

The final reviewer must record evidence for each open gate:

- **B7b:** a compatible existing application's executed scenario/report, with resolved critical correctness findings. Application selection and results remain outstanding.
- **B7c:** reproducible schema/record/lifecycle and browser-memory measurements, actual environment metadata, justified budgets and lower-powered-environment evidence. A synthetic Node measurement alone is insufficient. Optimize compiled planning only if measurements identify it as worthwhile.
- **B7d / AX2–AX4:** reconcile documentation with the final candidate, classify supported versus provisional exports, review migration impact and diagnostic usability, and verify installed JS/TS/Angular consumers after any resulting changes. Record whether the base can support the extension phase, with explicit limits and unresolved findings.
- **AX5 / stable:** separately review beta/stable release policy and compatibility/deprecation commitments. Existing scripts intentionally accept alpha; merging feature work or this audit does not authorize a version/channel change or merging the batched release PR.

Decision: **OPEN.** No completion checkbox changes solely because this inventory or trial protocol exists. Update the decision only after the required evidence and independent review are available.
