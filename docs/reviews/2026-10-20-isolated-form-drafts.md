# P4.4/P4.5 isolated form drafts and browser parity review

Independent reviewer: `foundation_review`, before the implementation commit on October 20, 2026.

Scope: shared demo-only draft policy, Angular reactive-form editors, Apollo/StateQL source bindings, explicit command acknowledgement handling, fixture removal/rejection controls, integration and browser tests, and documentation. No library package API or shared cache engine was changed.

The reviewer identified two P2 issues. First, a confirmed save's StateQL refresh initially reused the editor handle and could lose ownership if the editor left during the read. Every explicit refresh now owns an independent temporary narrow handle through settlement and disposes it in `finally`; browser tests gate the post-save read, switch every view to another tenant, then verify the old scope's cache without another request. Second, cached observations could unlock reconciliation after an unknown save acknowledgement. A separate required-read flag now clears only after a successful explicit refresh, not cached observations or failed reads. The reviewer rechecked both fixes and their regression tests with no remaining runtime findings.

The reviewer independently passed the 17-test demo suite during runtime review and the final 10 draft-policy/command-transport tests after validation additions. They reviewed the final docs and found a table-formatting issue, which was corrected. They agreed that the shared browser scenarios satisfy the P4.5 fixture matrix. The parent passed `pnpm check`: formatting, production builds, generated-schema checks, strict types, 199 tests (16 tooling, 81 core, 5 API, 56 GraphQL, 2 vanilla, 21 Angular, 18 demo), and isolated package/APF/AOT consumers. The final browser run passed all 25 cases: four Apollo baseline, five StateQL reads, and eight form-policy scenarios per client. Mobile form layout was visually inspected.

Coverage includes local draft isolation, pristine refresh, dirty conflicts and deliberate resolution, latest-server reset, null versus empty/unavailable values, validation, immutable submitted values and target identity, later typing, known rejection, uncertain acknowledgement, confirmed-save/failed-refresh recovery without write retry, tenant and record replacement, record removal, and disposal before or during the follow-up read. Both modes use the same HTTP command transport and editing policy; client bindings supply their native read/refresh semantics.

The parent also measured the preliminary fixture network result documented in `DEMO.md`: each client used two operations, with 453-byte full and 235-byte narrow response bodies. The reviewer checked the caveats but did not independently reproduce those byte measurements. This is not the P5 package/planning-cost evaluation or a claim of performance superiority. Server revision preconditions, streaming, durable writes and production form helpers remain outside scope.

Changes are limited to private demo applications, fixtures, tests and docs, so no Changeset is required. npm publication remains disabled; P5 and release preparation still precede the trusted-publisher setup handoff.
